Code Blocks & Scope
Variables declared inside {...} stay inside {...}

Block Scope

When you declare a variable with let or const inside a block, it is only visible inside that block. This lets you isolate code without naming collisions.

Works: Isolated Blocks

{ // Block 1
  let message = "Hello";
  alert(message); // Hello
}

{ // Block 2
  let message = "Goodbye";
  alert(message); // Goodbye
}

Each block has its own message. No conflict!

Error: No Block

let message = "Hello";
alert(message);

let message = "Goodbye"; // Error!
// Variable already declared

Without blocks, same-name variables collide.

Also Applies to Loops & Conditions

for (let i = 0; i < 3; i++) {
  // i is only visible inside this for loop
  alert(i); // 0, 1, 2
}

alert(i); // Error: i is not defined
Real-World Analogy

Hotel Rooms: Think of a code block like a hotel room. Two different rooms can each have a "towel" — they don't conflict. But you can't have two towels with the same name in the same room.

Nested Functions
Functions created inside other functions — and the magic of returning them

What is a Nested Function?

A function created inside another function. It can access the outer function's variables. But the real magic? A nested function can be returned and used elsewhere.

Helper Function

function sayHiBye(firstName, lastName) {

  // Helper nested function
  function getFullName() {
    return firstName + " " + lastName;
  }

  alert( "Hello, " + getFullName() );
  alert( "Bye, " + getFullName() );
}

Returning a Function ⭐

function makeCounter() {
  let count = 0;

  return function() {
    return count++;
  };
}

let counter = makeCounter();

alert( counter() ); // 0
alert( counter() ); // 1
alert( counter() ); // 2
The Big Question: After makeCounter() finishes, its local variables should be gone. So how does counter() still know about count? And if we create a second counter, are they independent? Let's find out!
Real-World Analogy

A factory machine: makeCounter is a factory that produces counter gadgets. Each gadget has its own internal counter dial. Even after the factory closes, each gadget keeps ticking on its own.

Lexical Environment: Variables
Under the hood — how JavaScript stores and finds variables

What is a Lexical Environment?

Every running function, code block, and the script itself has a hidden object called a Lexical Environment. It consists of two parts:

1. Environment Record

An object that stores all local variables as its properties (plus this value, etc.).

2. Outer Reference

A link to the outer Lexical Environment (the one surrounding this code).

Global Lexical Environment
phrase "Hello"
user "John"
[[Outer]] null

The global environment has no outer reference → points to null.

Variable Lifecycle in 3 Stages

1
Uninitialized: Engine knows the variable exists (via let), but you cannot access it yet. Accessing it throws an error.
2
Declared (undefined): The let line is reached. The variable now exists with value undefined until assigned.
3
Assigned: A value is given. The variable is ready to use!
Real-World Analogy

A filing cabinet: The Lexical Environment is a filing cabinet. Each drawer (Environment Record) holds folders (variables). If a folder isn't in this drawer, you check the connected cabinet (outer reference) next door.

Function Declarations & Scope Chain
How functions are initialized instantly, and how variable lookup works

Function Declarations are Instant

Unlike let variables, a Function Declaration is fully initialized the moment the Lexical Environment is created. That's why you can call it before its definition in the code!

// This works!
alert( say("John") );

function say(name) {
  return "Hello, " + name;
}
Note: This only works for Function Declarations, not Function Expressions like let say = function(name) {...}.

The Scope Chain Lookup

When code needs a variable, JavaScript searches in order:

Returning a Function & [[Environment]]
How the makeCounter function actually works under the hood

The Hidden [[Environment]] Property

All functions remember the Lexical Environment in which they were created. They carry a hidden [[Environment]] property that stores a reference to their birthplace. This reference is set once and forever at creation time.

function makeCounter() {
  let count = 0;

  return function() {
    return count++; // Where does 'count' come from?
  };
}

let counter = makeCounter();

Step 1: makeCounter() runs

makeCounter Environment
count0

A new Lexical Environment is created with count = 0. The returned function's [[Environment]] points here.

Step 2: counter() is called

counter() call Environment
(empty)
[[Outer]] →makeCounter Env

No local count? Follow outer reference → finds count in makeCounter's environment. Updates it there!

Key Insight: The variable is updated in the Lexical Environment where it lives, not where it's accessed from. Each call to makeCounter() creates a new, independent Lexical Environment with its own count.

What is a Closure?
The concept that makes JavaScript functions so powerful

Closure Definition

A closure is a function that remembers its outer variables and can access them.
In JavaScript, all functions are naturally closures.
They automatically remember where they were created using the hidden [[Environment]] property.

Interview Answer

If someone asks "What's a closure?", a great answer would be:

1
Define it: A function that remembers outer variables from its birthplace.
2
Key fact: In JS, all functions are closures by default.
3
Technical detail: They use the [[Environment]] property to reference their Lexical Environment.
4
Practical effect: Even if the outer function has finished running, the returned inner function still has access to its variables.
Real-World Analogy

Your phone's contacts: You might move to a different city (the function is called elsewhere), but you still have the contacts from your hometown (the outer variables). The contacts were saved when you got the phone (creation time), not when you moved (call time).

Garbage Collection & Closures
How Lexical Environments stay alive (and when they die)

The Rule of Reachability

Normally, when a function finishes, its Lexical Environment is garbage collected (removed from memory) because nothing references it anymore. But closures change this!

Kept Alive

function f() {
  let value = 123;

  return function() {
    alert(value);
  };
}

let g = f();
// g.[[Environment]] references
// f's Lexical Environment
// → value stays in memory!

As long as g exists, the environment (and value) is reachable and stays alive.

Cleaned Up

function f() {
  let value = 123;

  return function() {
    alert(value);
  };
}

let g = f();
// ... later ...
g = null; // Now cleaned up!

Once g is removed, nothing references the Lexical Environment. value is garbage collected.

Multiple Instances = Multiple Environments

function f() {
  let value = Math.random();
  return function() { alert(value); };
}

// 3 different functions, 3 different environments
let arr = [f(), f(), f()];

Each call to f() creates its own independent Lexical Environment. All 3 stay in memory as long as the arr array exists.

Real-Life Optimizations & Debugging
A V8 engine quirk that might surprise you in Chrome DevTools

Engine Optimizations

In theory, while a function exists, all outer variables are retained. In practice, engines like V8 (Chrome, Edge, Opera) optimize memory by removing unused variables from the Lexical Environment.

The Debugging Gotcha

Try this in Chrome DevTools — the variable value won't be available even though it theoretically should be:

function f() {
  let value = Math.random();

  function g() {
    debugger; // In console: alert(value);
    // Error: value is not defined!
  }

  return g;
}

let g = f();
g();

V8 saw that g() doesn't use value and removed it to save memory. This can be confusing during debugging!

The Phantom Variable

Even stranger — a same-named variable from an outer scope might appear instead:

let value = "Surprise!";

function f() {
  let value = "the closest value";

  function g() {
    debugger; // alert(value) → "Surprise!"
    // The inner 'value' was optimized out,
    // so it finds the outer one!
  }

  return g;
}
Good to know: This is not a debugger bug — it's a V8 optimization feature. If you're debugging in Chrome/Edge/Opera and a variable is missing or showing a wrong value, this might be why.

Summary
Everything you need to remember about Scope & Closures

Block Scope

  • let/const inside {...} are block-scoped
  • Variables only exist within their block
  • For loops have their own scope per iteration

Lexical Environment

  • Environment Record (local variables) + outer reference
  • Variable lookup goes: inner → outer → global
  • Function Declarations are initialized instantly

Closures

  • All JS functions are closures
  • They remember their birthplace via [[Environment]]
  • Outer variables stay alive as long as the function exists

Garbage Collection

  • Lexical Environments live while reachable
  • Setting func = null allows cleanup
  • V8 may optimize away unused variables (debugging gotcha)
