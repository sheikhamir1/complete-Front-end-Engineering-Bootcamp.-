Two Kinds of Properties
Data properties vs. Accessor properties

What's the Difference?

Until now, we've only used data properties — simple key-value pairs. But there's a second type: accessor properties. They look like regular properties from the outside, but are actually functions that run when you read or write.

Data Property

Stores a value directly.

let user = {
  name: "John" // Data property
};

alert(user.name); // "John"

Accessor Property

Runs a function when read or written.

let user = {
  get fullName() {
    return "John Smith";
  }
};

alert(user.fullName); // "John Smith"
The Magic: From the outside, user.fullName looks like a normal property. You don't call it like user.fullName(). You just read it, and the getter function runs behind the scenes!
Real-World Analogy

Whiteboard vs. Receptionist: A data property is like a whiteboard — you look at it and see what's written. An accessor property is like asking a receptionist "What's John's full name?" — the receptionist does the work of combining the first and last name and gives you the answer.

Getter & Setter Syntax
How to define accessor properties in an object literal

The Basic Structure

Getters and setters are defined using the get and set keywords inside an object literal.

let obj = {
  get propName() {
    // Runs when you READ obj.propName
  },

  set propName(value) {
    // Runs when you WRITE obj.propName = value
  }
};

Example: fullName

let user = {
  name: "John",
  surname: "Smith",

  get fullName() {
    return `${this.name} ${this.surname}`;
  },

  set fullName(value) {
    [this.name, this.surname] = value.split(" ");
  }
};

alert(user.fullName); // John Smith (getter runs)

user.fullName = "Alice Cooper"; // (setter runs)
alert(user.name); // Alice
alert(user.surname); // Cooper
Read-Only: If you only define a get without a set, the property becomes read-only. Attempting to assign it will throw an error: user.fullName = "Test"; // Error (property has only a getter)

Accessor Descriptors
Using Object.defineProperty with getters and setters

Different Descriptors

Accessor properties have different descriptor flags than data properties. There is no value or writable. Instead, there are get and set functions.

Attribute Data Property Accessor Property
Value value ❌ (not allowed)
Writability writable ❌ (not allowed)
Getter ❌ (not allowed) get
Setter ❌ (not allowed) set
Visibility enumerable enumerable
Configurability configurable configurable

Example with defineProperty

Object.defineProperty(user, 'fullName', {
  get() { return `${this.name} ${this.surname}`; },
  set(value) { [this.name, this.surname] = value.split(" "); }
});
Cannot Mix! A property can be either an accessor (has get/set) OR a data property (has value), but never both. Supplying both get and value in the same descriptor throws an error!

Smarter Getters/Setters
Using accessors as wrappers to add validation and control

Adding Validation

Getters and setters can act as "bouncers" for your data. They wrap the real value and check any incoming changes before allowing them through.

let user = {
  get name() {
    return this._name;
  },

  set name(value) {
    if (value.length < 4) {
      alert("Name is too short, need at least 4 characters");
      return; // Reject the change!
    }
    this._name = value;
  }
};

user.name = "Pete"; // Stored successfully
alert(user.name); // Pete

user.name = ""; // "Name is too short..." (rejected!)
Real-World Analogy

Club Bouncer: The setter is like a bouncer at a club door. You try to enter (assign a value), but the bouncer checks if you meet the rules (at least 4 characters). If you don't, you're turned away. If you do, you're let inside (stored in _name).

The Underscore Convention
How to store the "real" value behind a getter/setter

Why _name?

In the previous example, we stored the value in this._name, not this.name. Why? Because if we used this.name, the setter would call itself endlessly!

Infinite Loop!

set name(value) {
  this.name = value; // Calls setter again!
  // → Stack Overflow!
}

Correct Way

set name(value) {
  this._name = value; // Stores in _name
  // → No infinite loop
}

The Convention

Properties starting with an underscore _ are internal properties. It's a widely known convention among developers: "Don't touch properties starting with _ from outside the object."

  • Technically, external code can access user._name
  • But by convention, they shouldn't — it's the object's private business
  • Always use the getter/setter (user.name) instead
Real-World Analogy

Employees Only Door: A door with an "Employees Only" sign. There's no physical lock stopping customers from walking in, but the sign tells them they shouldn't. The _ prefix is that sign for other programmers.

Using for Compatibility
Refactoring internal data without breaking old code

The Problem

Imagine we started with a simple age data property, but later realized birthday is more precise. How do we change the internal structure without breaking old code that uses age?

Old Code

function User(name, age) {
  this.name = name;
  this.age = age;
}

let john = new User("John", 25);
alert(john.age); // 25

New Code (Compatible!)

function User(name, birthday) {
  this.name = name;
  this.birthday = birthday;

  Object.defineProperty(this, "age", {
    get() {
      let year = new Date().getFullYear();
      return year - this.birthday.getFullYear();
    }
  });
}
Result: Old code using john.age still works perfectly! The getter computes the age dynamically from the birthday. No need to find and update every place that uses .age.
Real-World Analogy

Car Speedometer: Old cars used a physical cable from the wheel to the dashboard. New cars calculate speed from wheel sensors electronically. But the driver still just looks at the same "Speed" dial on the dashboard. The internal implementation changed, but the interface (getter) stayed the same.

Data vs Accessor Comparison
When to use which kind of property
Aspect Data Property Accessor Property
What it stores A direct value Functions (get/set)
When to use Simple data that doesn't need validation or computation Computed values, validation, compatibility wrappers
Descriptor keys value, writable, enumerable, configurable get, set, enumerable, configurable
Can mix? ❌ No! A property is either data OR accessor, never both.

When to Use Accessors

  • Computed values: Like fullName from name + surname
  • Validation: Rejecting invalid values before they're stored
  • Logging/Tracking: Noting when a property is read or changed
  • Lazy calculation: Computing a value only when it's first needed
  • Compatibility: Keeping old property names working after internal refactoring
Don't Overuse: If a property is just storing a simple value with no logic needed, use a regular data property. Getters/setters add complexity — only use them when you actually need the control.

Summary
Everything you need to remember about Getters & Setters

Key Concepts

  • Accessor properties look like data, but run functions
  • get runs when you read the property
  • set runs when you assign to the property
  • Only get = read-only property
  • Cannot mix value and get in descriptors

Best Practices

  • Use _ prefix for internal storage properties
  • Use setters for validation and logging
  • Use getters for computed/derived values
  • Use for backward compatibility when refactoring
  • Don't overuse — simple data doesn't need accessors
