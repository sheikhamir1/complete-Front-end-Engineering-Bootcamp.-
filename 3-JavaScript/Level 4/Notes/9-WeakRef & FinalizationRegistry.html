WeakRef & FinalizationRegistry

Managing Memory at the Edge of JavaScript

JavaScript automatically cleans up memory using a Garbage Collector. It deletes objects that are no longer reachable. But what if we want to hold onto an object without forcing it to stay in memory? That's where WeakRef and FinalizationRegistry come in.

⚠️ Advanced Feature Warning: These are "hidden" features used very rarely. Most developers never need them. However, understanding them helps you grasp how JavaScript memory really works under the hood!

Strong vs. Weak References

The difference that controls memory

Strong References (The Default)

When you assign an object to a variable, you create a strong reference. As long as that variable exists, the Garbage Collector (GC) will never delete the object.

let user = { name: "John" }; // Strong reference user = null; // Reference lost. Object is deleted from memory.

Weak References (WeakRef)

A weak reference points to an object, but does not prevent the Garbage Collector from deleting it. If the only things left pointing to an object are weak references, the GC is free to destroy it.

Real-World Analogy: Imagine a balloon. A strong reference is like holding the balloon's string tightly—it won't fly away. A weak reference is like just pointing at the balloon. If the person holding the string lets go, the balloon flies away (gets deleted), regardless of who is pointing at it!

Creating a WeakRef

let user = { name: "John" }; // Create a weak reference to the user object let admin = new WeakRef(user); // Now, if we remove the strong reference... user = null; // The object can now be deleted by the GC, even though 'admin' still exists.

Reading WeakRefs with deref()

Schrödinger's Object

Is it alive or dead?

Because the Garbage Collector runs unpredictably, we never know exactly when a WeakRef's object will be deleted. It becomes like "Schrödinger's cat"—it might be in memory, or it might be gone.

To check if the object still exists and access it, we use the deref() method.

Using deref()

let user = { name: "John" }; let weakUser = new WeakRef(user); // Try to get the object let ref = weakUser.deref(); if (ref) { alert(ref.name); // "John" (Object is still alive!) } else { alert("Object has been garbage collected."); // It's dead. }
Rule of Thumb: If deref() returns the object, it's safe to use for that moment. If it returns undefined, the GC ate it, and you must recreate the object (e.g., fetch it from a server again).

Use Case: Smart Caching

Saving memory without leaks

Imagine we download massive images (as Blobs or ArrayBuffers). We want to cache them so we don't re-download them, but we don't want the cache to crash the browser by eating all the RAM.

Map keeps objects alive forever (memory leak!). WeakMap doesn't let us use strings as keys. The solution? A Map with WeakRef values!

The WeakRef Cache

function weakRefCache(fetchImg) { const imgCache = new Map(); // Keys are strings, values are WeakRefs return (imgName) => { const cachedImg = imgCache.get(imgName); // If it exists in cache AND hasn't been garbage collected... if (cachedImg?.deref()) { return cachedImg.deref(); // Cache hit! } // Otherwise, download it fresh const newImg = fetchImg(imgName); // Store it in cache wrapped in a WeakRef imgCache.set(imgName, new WeakRef(newImg)); return newImg; }; }

The Problem: Over time, the Map fills up with string keys pointing to "dead" WeakRefs whose objects were deleted. We need a way to clean up the keys too!

FinalizationRegistry

The Cleanup Callback

What is a Finalizer?

A FinalizationRegistry lets you register a cleanup callback (a finalizer) that runs automatically when an object is finally destroyed by the Garbage Collector.

Real-World Analogy: Think of it like an Executor of a Will. When the person (the object) passes away (gets garbage collected), the executor automatically steps in to fulfill their final wishes (run the cleanup callback).

Creating a Registry

// 1. Create the registry with a cleanup callback const registry = new FinalizationRegistry((heldValue) => { console.log(`${heldValue} was deleted by the Garbage Collector.`); }); // 2. Create an object and register it let user = { name: "John" }; // register(target, heldValue) // When 'user' is deleted, it will pass "John" to the callback. registry.register(user, user.name); // 3. Remove the strong reference user = null; // Sometime later... GC runs, and the console logs: // "John was deleted by the Garbage Collector."
⚠️ Timing is not guaranteed: You don't control the GC. The callback might run much later, or not at all if the browser tab closes first.

The Perfect Cache

Combining WeakRef & FinalizationRegistry

Let's fix our earlier cache problem. We will use FinalizationRegistry to automatically delete the "dead" string keys from the Map when their WeakRef values are garbage collected.

Upgraded Cache Code

function weakRefCache(fetchImg) { const imgCache = new Map(); // 1. Create a registry to clean up dead keys const registry = new FinalizationRegistry((imgName) => { const cachedImg = imgCache.get(imgName); // Make sure it hasn't been re-added before deleting! if (cachedImg && !cachedImg.deref()) imgCache.delete(imgName); }); return (imgName) => { const cachedImg = imgCache.get(imgName); if (cachedImg?.deref()) return cachedImg.deref(); const newImg = fetchImg(imgName); imgCache.set(imgName, new WeakRef(newImg)); // 2. Register the new image so its key is cleaned up later registry.register(newImg, imgName); return newImg; }; }
Why check !cachedImg.deref() in the callback? Because the main program and the cleanup callback run in parallel. You might delete an object, but right before the callback runs, the main program fetches and adds a new object under the exact same key. We must ensure we don't accidentally delete a fresh, "live" object!

Real-World Scenario: Photo App

Saving network requests & RAM

Imagine a cloud photo app (like iCloud). You see tiny thumbnails, but when you click "Create Collage", the app needs the full-size, high-res images.

The Process

  • 1. First Collage: App fetches 4 high-res images. It caches them using our weakRefCache. Memory usage goes up.
  • 2. Idle Time: User browses other photos. The GC notices the 4 high-res images aren't strongly referenced and deletes them to free up RAM. The registry cleans the cache keys.
  • 3. Second Collage: User makes another collage. 1 image is still in RAM (cache hit!). 3 were deleted by GC and must be re-fetched from the cloud.

The Result

Using this approach, we balance speed and memory:

If the user makes collages quickly, the images are still in the cache (super fast!). If they wait a while, the GC cleans up the massive images so the browser doesn't crash (safe!).

This prevents the browser from holding onto hundreds of megabytes of high-res images just in case the user wants them again.

Summary

When to use, and when NOT to

WeakRef

Allows you to point to an object without keeping it alive. Use deref() to check if it still exists. Great for caching heavy objects where memory is a concern.

FinalizationRegistry

Lets you register a cleanup callback that runs after the Garbage Collector deletes an object. Perfect for cleaning up "dead" keys in a cache or closing file handles.

Why not use them everywhere?

Most of the time, you don't need them! Normal caching logic (like LRU caches) is predictable and reliable. WeakRef and FinalizationRegistry rely on the Garbage Collector, which is unpredictable. You never know exactly when memory will be freed or when a callback will run.

Golden Rule: Only use these advanced features when you have strict memory constraints with heavy objects, and always ensure your code works correctly even if the Garbage Collector deletes the objects immediately!
