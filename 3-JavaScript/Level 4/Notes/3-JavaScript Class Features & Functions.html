Static Properties & Methods

Belonging to the Class, Not the Object

What does "Static" mean?

Normally, methods are called on an instance of a class (an object). Static methods are called on the class itself.

Real-World Analogy: Think of a Car Factory vs. a specific Car. The factory (Class) can buildCar(), but a specific car (Instance) can drive(). You don't ask your car to build another car; you ask the factory!

Static Method

class User { static staticMethod() { alert(this === User); } } // Called on the Class, not an instance User.staticMethod(); // true

Static Property

class Article { static publisher = "Ilya Kantor"; } alert(Article.publisher); // Ilya Kantor // Same as: Article.publisher = "Ilya Kantor";

Important: Static methods are NOT available on individual objects.

let article = new Article(); article.staticMethod(); // Error: not a function

Static Use Cases

Comparing & Factory Methods

1. Comparing Objects

Sometimes we need a function that compares two instances of a class. It logically belongs to the class, but doesn't belong to a single object.

class Article { constructor(title, date) { this.title = title; this.date = date; } static compare(articleA, articleB) { return articleA.date - articleB.date; } } let articles = [ new Article("HTML", new Date(2019, 1, 1)), new Article("CSS", new Date(2019, 0, 1)) ]; articles.sort(Article.compare); alert(articles[0].title); // CSS

2. Factory Methods

Need multiple ways to create an object? A constructor only handles one way. Static methods can create objects with specific defaults.

class Article { constructor(title, date) { this.title = title; this.date = date; } static createTodays() { // remember, this = Article return new this("Today's digest", new Date()); } } let article = Article.createTodays(); alert(article.title); // Today's digest
Database Analogy: Static methods are often used for database operations like Article.remove({id: 12345}) or User.findById(1). You ask the whole class to find/remove something, not one specific user.

Inheritance of Statics

Static properties & methods pass down to children

How it works

When we use extends, static methods and properties are also inherited. Under the hood, the child class's prototype points to the parent class.

class Animal { static planet = "Earth"; constructor(name, speed) { this.speed = speed; this.name = name; } static compare(animalA, animalB) { return animalA.speed - animalB.speed; } } class Rabbit extends Animal { hide() { alert(`${this.name} hides!`); } } let rabbits = [ new Rabbit("White Rabbit", 10), new Rabbit("Black Rabbit", 5) ]; // Rabbit inherits Animal.compare rabbits.sort(Rabbit.compare); // Rabbit inherits Animal.planet alert(Rabbit.planet); // Earth
The Prototype Chain:
Rabbit.__proto__ === Animal (For static methods)
Rabbit.prototype.__proto__ === Animal.prototype (For instance methods)

Private & Protected Properties

Encapsulation: Hiding the Internal Interface

The Coffee Machine Analogy

Think of a coffee machine. From the outside, you see buttons (External Interface). Inside, there are tubes and heaters (Internal Interface).

If the protective cover is removed, it becomes dangerous and confusing. In programming, we want to hide the complex/dangerous parts so others can use our code safely.

External Interface (Public)

Methods and properties that anyone can use from outside. Like the "Brew Coffee" button.

Internal Interface (Private/Protected)

Methods and properties only accessible from inside the class. Like the heating element.

Why hide the internals? (Benefits of Encapsulation)

  • Protection: Prevents users from breaking things they shouldn't touch (e.g., setting water amount to negative).
  • Supportable: You can rewrite the internal code without breaking everyone's code, as long as the external buttons still work.
  • Hiding Complexity: Users don't need to understand how the heater works to make coffee.

Protected Properties

Using the Underscore Convention (_)

The Underscore _ Convention

JavaScript doesn't have a native "protected" keyword. Instead, developers use an underscore _ in front of the property name. This is a polite way of saying: "Please don't touch this from outside the class!"

Real-World Analogy: A "Staff Only" sign on a door. It's not a locked door (you can still open it if you want), but you know you shouldn't.

Controlling Access with Getters/Setters

class CoffeeMachine { _waterAmount = 0; // Protected property set waterAmount(value) { if (value < 0) value = 0; // Protection logic! this._waterAmount = value; } get waterAmount() { return this._waterAmount; } } let machine = new CoffeeMachine(); machine.waterAmount = -10; // _waterAmount becomes 0, not -10!

Read-Only Properties

If you only provide a get and no set, the property becomes read-only. For example, a coffee machine's power shouldn't change after it's built.

class CoffeeMachine { constructor(power) { this._power = power; } get power() { return this._power; } } let coffeeMachine = new CoffeeMachine(100); coffeeMachine.power = 25; // Error (no setter)

Private Properties

Enforced Privacy with the Hash (#)

The Hash # Syntax

Unlike the underscore, the # prefix is enforced by the JavaScript engine. Nobody can access it from outside.

Real-World Analogy: A locked safe. It is physically impossible to open it without the key. The language itself blocks access.

Creating Private Fields

class CoffeeMachine { #waterLimit = 200; // Private property #fixWaterAmount(value) { // Private method if (value < 0) return 0; if (value > this.#waterLimit) return this.#waterLimit; } setWaterAmount(value) { this._waterAmount = this.#fixWaterAmount(value); } } let machine = new CoffeeMachine(); machine.#fixWaterAmount(123); // Error! Can't access from outside machine.#waterLimit = 1000; // Error!

Private vs Protected

Feature Protected (_) Private (#)
Enforced by JS engine? No (Gentleman's agreement) Yes (Hard error if violated)
Accessible in child classes? Yes No
Can have same public name? No (conflict) Yes (e.g., #water and water)

Rest Parameters & Spread Syntax

Mastering the ... Operator

Rest Parameters ...

Sometimes you don't know how many arguments a function will receive. Rest parameters gather the remaining arguments into a real Array.

Real-World Analogy: Packing a suitcase. You have specific items on top, and then you pack the rest of your clothes into the remaining space.

Gathering Arguments

// Gather ALL arguments into an array called 'args' function sumAll(...args) { let sum = 0; for (let arg of args) sum += arg; return sum; } alert( sumAll(1, 2, 3) ); // 6 // First arguments as variables, the REST in an array function showName(firstName, lastName, ...titles) { alert( firstName + ' ' + lastName ); // Julius Caesar alert( titles[0] ); // Consul alert( titles[1] ); // Imperator } showName("Julius", "Caesar", "Consul", "Imperator");

The arguments Object

In old JavaScript, there was no ... syntax. People used the arguments object. It still works, but it's array-like, not a real array (no .map() or .filter()). Also, arrow functions don't have their own arguments. Always prefer Rest Parameters!

Spread Syntax

Unpacking Arrays & Iterables

From Array to List of Arguments

Spread syntax does the exact opposite of Rest. It takes an array and expands (unpacks) it into individual items.

Real-World Analogy: Unpacking a suitcase. You take the tightly packed bag and explode its contents out onto the bed as individual items.

Using Spread to Pass Arrays

let arr = [3, 5, 1]; // Math.max needs individual numbers: (3, 5, 1) // Not an array: ([3, 5, 1]) alert( Math.max(arr) ); // NaN (fails) // Spread unpacks the array! alert( Math.max(...arr) ); // 5 (works!) // You can even combine multiple arrays let arr1 = [1, -2, 3, 4]; let arr2 = [8, 3, -8, 1]; alert( Math.max(...arr1, ...arr2) ); // 8

Merging Arrays & Strings

// Merge arrays let merged = [0, ...arr, 2, ...arr2]; // [0, 3, 5, 1, 2, 8, 3, -8, 1] // Turn string into array of characters let str = "Hello"; alert( [...str] ); // H,e,l,l,o
Array.from vs Spread: Array.from(obj) works on both array-likes and iterables. Spread [...obj] only works on iterables. When in doubt, Array.from is safer.

Copying Objects & Arrays

A cleaner way to clone data

Shallow Copying with Spread

Spread provides a very clean shorthand for making copies of arrays and objects. It does the same thing as Object.assign(), but is shorter to write.

Copying Arrays

let arr = [1, 2, 3]; // Spread into a new array let arrCopy = [...arr]; alert(arr === arrCopy); // false (new reference) arr.push(4); alert(arrCopy); // 1, 2, 3 (unaffected)

Copying Objects

let obj = { a: 1, b: 2, c: 3 }; // Spread into a new object let objCopy = { ...obj }; alert(obj === objCopy); // false (new reference) obj.d = 4; alert(JSON.stringify(objCopy)); // {"a":1,"b":2,"c":3}

Summary: Rest vs Spread

Feature Rest Parameters ... Spread Syntax ...
Purpose Gather items into an array Expand array into items
Location Function definition (parameters) Function call or literals (arrays/objects)
Analogy Packing a suitcase Unpacking a suitcase
