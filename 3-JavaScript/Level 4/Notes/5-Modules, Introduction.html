Modules, Introduction

Splitting Code for Scalable Apps

As our application grows, keeping everything in one file becomes a nightmare. We need to split it into multiple files called "modules". A module may contain a class or a library of functions for a specific purpose.

Real-World Analogy: Think of a kitchen. Instead of throwing all your utensils, ingredients, and appliances into one massive drawer (one big file), you organize them. Cutlery in one drawer, spices in the cabinet, pots under the stove. Each drawer is a module.

For a long time, JavaScript didn't have a built-in module system, so the community invented workarounds like AMD, CommonJS, and UMD. But in 2015, JavaScript finally got a native, language-level module system. We will focus on this modern standard.

What is a Module?

Exporting & Importing

A Module is Just a File

As simple as that. One script is one module. Modules can load each other and use special directives to interchange functionality:

  • export: Labels variables and functions that should be accessible from outside the current module.
  • import: Allows the import of functionality from other modules.

📁 sayHi.js (Exporting)

export function sayHi(user) { alert(`Hello, ${user}!`); }

📁 main.js (Importing)

import {sayHi} from './sayHi.js'; alert(sayHi); // function... sayHi('John'); // Hello, John!

HTML Setup

We must tell the browser that a script should be treated as a module by using the attribute type="module".

<script type="module"> import {sayHi} from './say.js'; document.body.innerHTML = sayHi('John'); </script>
Important: Modules work only via HTTP(s), not locally. If you try to open a web-page locally via file://, import/export won't work. Use a local web-server (like VS Code Live Server).

Core Module Features

Strict Mode & Local Scope

1. Always "use strict"

Modules always work in strict mode automatically. You can't turn it off. E.g., assigning to an undeclared variable will throw an error.

<script type="module"> a = 5; // Error: undeclared variable </script>

2. Module-Level Scope

Each module has its own top-level scope. Top-level variables from a module are not seen in other scripts.

Analogy: Variables in one module are like private thoughts. They stay in your head unless you speak them out loud (export).

The Wrong Way vs. The Right Way

// 📁 user.js let user = "John"; // NOT exported // 📁 hello.js import {user} from './user.js'; // Error! user is hidden. // --- THE CORRECT WAY --- // 📁 user.js export let user = "John"; // Exported! // 📁 hello.js import {user} from './user.js'; // Works!

Note: We should avoid making global variables like window.user = "John". Modules are designed to eliminate global scope pollution. Use import/export instead!

Evaluated Only Once

Sharing the Same Instance

Single Execution Rule

If the same module is imported into multiple other modules, its code is executed only once, upon the first import. Then its exports are given to all further importers.

Real-World Analogy: Imagine starting a car engine. You turn the key once. Even if multiple passengers (importers) want to use the AC or radio (exports), the engine (module code) doesn't restart for each one. It runs once, and everyone shares its power.

Sharing the Same Object

Because of this rule, if a module exports an object, all importers get exactly the same object. If one importer changes it, the others will see the change!

// 📁 admin.js export let admin = { name: "John" }; // 📁 1.js import {admin} from './admin.js'; admin.name = "Pete"; // Changed! // 📁 2.js import {admin} from './admin.js'; alert(admin.name); // 'Pete' (Sees the change!)

The Configuration Pattern

This behavior is great for configuring a module once at startup, and having that configuration apply everywhere else automatically.

// 📁 admin.js export let config = { }; export function sayHi() { alert(`Ready, ${config.user}!`); } // 📁 init.js (Runs first, sets it up) import {config} from './admin.js'; config.user = "Pete"; // 📁 another.js (Runs later) import {sayHi} from './admin.js'; sayHi(); // Ready, Pete!

Minor Features: import.meta & this

Module-specific details

import.meta

The object import.meta contains information about the current module.

In the browser, it contains the URL of the script:

<script type="module"> alert(import.meta.url); // e.g., "https://site.com/my.js" </script>

"this" is undefined

In a module, top-level this is undefined.

Compare it to non-module scripts, where this is the global object (window):

<script> alert(this); // window </script> <script type="module"> alert(this); // undefined </script>
Why does this matter? It prevents accidental modifications to the global window object. Modules force you to be intentional about where your data lives.

Browser-Specific Features

How modules behave in the browser

1. Module Scripts are Deferred

Module scripts always act like they have a defer attribute. They download in the background (without blocking HTML) and wait until the HTML is fully loaded before running.

2. Async Works on Inline Scripts

For normal scripts, async only works on external files. For modules, async works on inline scripts too! This is great for independent things like analytics that shouldn't block the page.

<script async type="module"> import {counter} from './analytics.js'; counter.count(); // Runs as soon as ready </script>

3. External Scripts Run Once

If you link the same script twice, it only runs once.

<!-- my.js runs only once --> <script type="module" src="my.js"></script> <script type="module" src="my.js"></script>

4. CORS Required

Fetching a module from another site requires CORS headers (permission from the other server).

5. No "Bare" Modules

In the browser, you must provide a relative or absolute URL. You cannot just use a name.

import {sayHi} from 'sayHi'; // Error! No path. import {sayHi} from './sayHi.js'; // Correct!

Build Tools & "nomodule"

Preparing Modules for Production

The Fallback: "nomodule"

Old browsers don't understand type="module" and will ignore the script. We can provide a fallback using the nomodule attribute for older browsers.

<script type="module"> alert("Runs in modern browsers"); </script> <script nomodule> alert("Modern browsers ignore this. Old browsers run this."); </script>

Build Tools (Webpack, Vite, etc.)

In real-life, browser modules are rarely used in their "raw" form. Usually, we bundle them together with a tool like Webpack or Vite.

Real-World Analogy: Imagine moving to a new house. Instead of carrying 50 small boxes (50 module files) one by one, you pack them all into one giant shipping container (bundle.js). It's much more efficient to transport!

What Build Tools Do:

  • Bundle: Take the main module and all its imports, combining them into one (or a few) files.
  • Tree-shaking: Remove unused exports to save space.
  • Transform: Convert modern JS to older JS so older browsers understand it.
  • Minify: Remove spaces and shorten variable names to make files smaller.

After bundling, the final script doesn't need type="module" because it no longer contains import/export statements. It's just a regular script!

<!-- Assuming we got bundle.js from Webpack --> <script src="bundle.js"></script>
