Export & Import

Sharing Code Like a Pro

Modules are all about sharing code between files. In JavaScript, we use export to make variables, functions, or classes available to other files, and import to bring them in.

Real-World Analogy: Think of a restaurant. The kitchen (export) prepares dishes and puts them on the menu. The customers (import) look at the menu and order exactly what they want.

In this presentation, we'll explore the different ways to export and import, including how to load code dynamically only when you need it!

The Basics of Export

Putting things on the menu

1. Export Before Declarations

The easiest way to export is to put the export keyword right in front of the variable, function, or class you want to share.

// Export an array export let months = ['Jan', 'Feb', 'Mar']; // Export a constant export const YEAR = 2015; // Export a class (No semicolon needed!) export class User { constructor(name) { this.name = name; } }

2. Export Apart from Declarations

Sometimes it's cleaner to write all your code first, and then export exactly what you want at the very bottom of the file.

// 📁 say.js function sayHi(user) { alert(`Hello, ${user}!`); } function sayBye(user) { alert(`Bye, ${user}!`); } // Export list at the bottom export {sayHi, sayBye};

Import Variations

Ordering from the menu

Import Specifics

Usually, we list exactly what we need in curly braces. This is the best practice because it makes it clear exactly what your file depends on.

import {sayHi, sayBye} from './say.js'; sayHi('John'); // Hello, John!

Import Everything (*)

If a module has a lot to offer, you can import everything as a single object. Note: Modern tools (like Webpack) will remove the stuff you don't use, so don't worry about file size!

import * as say from './say.js'; say.sayHi('John'); // Hello, John! say.sayBye('John'); // Bye, John!

Aliasing with "as"

Sometimes names are too long, or you just want to call them something else locally. You can use the as keyword to give them a nickname.

Import Aliases

import {sayHi as hi, sayBye as bye} from './say.js'; hi('John'); // Hello, John!

Export Aliases

export {sayHi as hi, sayBye as bye}; // Outsiders must use hi() and bye()

Export Default

The "Main Star" of the Module

In practice, there are two types of modules. Ones that pack many functions (like a utility belt), and ones that exist just to hold one single thing (like a User class). For the latter, we use export default.

Real-World Analogy: Think of export default as the "Chef's Special" at a restaurant. You don't even need to know its exact name on the menu; you just order "the special". There can only be ONE Chef's Special per menu (module).

Exporting the Default

// 📁 user.js export default class User { constructor(name) { this.name = name; } } // No curly braces needed! And name is optional: export default class { ... } export default function() { ... }

Importing the Default

// 📁 main.js // NO curly braces! We can name it whatever we want. import User from './user.js'; new User('John'); // This also works (but stick to the filename!) import MyUser from './user.js';

Named vs Default

Feature Named Export Default Export
Syntax export class User {...} export default class User {...}
Import Syntax import {User} from ... import User from ...
Import Name Must match exactly Can be any name you choose
Per Module Unlimited Only ONE

The Debate: Named vs Default

Why some teams prefer Named Exports

The Problem with Defaults

Because you can name a default import anything, team members might import the same file using different names, which causes confusion.

// 📁 user.js export default class { ... } // 📁 dev1.js import User from './user.js'; // Developer 1 calls it User // 📁 dev2.js import Person from './user.js'; // Developer 2 calls it Person! Confusing!

The Solution: Stick to Filenames

If you use default exports, the industry standard rule is to name your import the same as the file name (just capitalized). E.g., user.js → import User.

Why some teams ONLY use Named Exports

Named exports force you to use the exact name, making the code consistent. They also make "Re-exporting" easier, which we'll look at next.

// Named exports require exact names import {User} from './user.js'; import {MyUser} from './user.js'; // ERROR! Won't work.

Re-exporting

Creating a Package Entry Point

The Mall Directory Concept

Imagine you are building a big package (like an authentication system) spread across many files. You don't want users of your package digging through your folders to find specific files. You want one "Front Desk" or "Directory" to answer all their questions.

Re-exporting means importing something just to immediately export it again. It lets you gather all your package's features into a single, easy-to-find file (like index.js).

The Long Way

// 📁 auth/index.js import {login, logout} from './helpers.js'; export {login, logout}; import User from './user.js'; export {User};

The Short Way (Re-export)

// 📁 auth/index.js export {login, logout} from './helpers.js'; // Re-exporting a Default as a Named export export {default as User} from './user.js';

Important Re-export Rules

  • Code isn't available locally: When you export ... from, you can't actually use that code inside the current file. It just passes it through.
  • Defaults need special handling: export * from './user.js' only re-exports named exports, ignoring the default one.
  • To re-export a default AND named exports, you need two lines:
    export * from './user.js'; // Gets named exports export {default} from './user.js'; // Gets the default

Dynamic Imports

Loading Code On-Demand

The Limitation of Static Imports

All the import/export statements we've seen are "static". They must be at the top level, and they run immediately when the file loads. You cannot put them inside if statements or functions.

if (userIsVIP) { import {discount} from './sales.js'; // ERROR! Not allowed! }

The Solution: import()

The import(modulePath) expression loads a module dynamically, exactly when you ask it to. It returns a Promise that resolves with the module's exports.

Real-World Analogy: A static import is like a bus schedule—the bus leaves at 8 AM whether you are there or not. A dynamic import is like calling an Uber—it only shows up exactly when and where you need it.

Using Dynamic Import

async function loadModule() { // The code inside say.js is NOT loaded until this function runs! let say = await import('./say.js'); say.hi(); // Hello! say.bye(); // Bye! // If say.js had a default export: say.default(); // Module loaded! }

Why do this? Performance! If you have a huge video player module, you don't need to load it when the user just opened your text-based article. Only load it when they click "Play Video". Dynamic imports work in regular scripts, they don't require type="module".
