Task Used for All Examples

👉 Find the maximum of two numbers

Why this task?

  • Simple enough to understand quickly
  • Complex enough to show different approaches
  • Can be implemented in many styles
  • Allows us to focus on the style, not the logic
We'll implement this same task in 9 different coding styles to compare approaches.

1️⃣ Clean / Readable Style (Best practice)

function max(a, b) {
  if (a > b) {
    return a;
  }
  return b;
}

Characteristics:

  • Clear, straightforward logic
  • Descriptive function name
  • Proper indentation
  • Easy to understand at a glance
This is the recommended approach for most production code. It prioritizes clarity over cleverness.

2️⃣ Ninja Style 🥷

Short, clever, slightly tricky

const max = (a, b) => a > b ? a : b;

Characteristics:

  • Uses arrow function syntax
  • One-liner with ternary operator
  • Very concise
  • Requires understanding of ES6+ features
While elegant, this style can be harder for beginners to understand and may not be suitable for all codebases.

3️⃣ Competitive Programming Style

Fast to write, short names

const mx = (a, b) => a > b ? a : b;

Characteristics:

  • Abbreviated function name (mx instead of max)
  • Optimized for typing speed
  • Common in coding competitions
  • Values brevity over readability
This style is useful in time-limited environments but should be avoided in production code where maintainability is important.

4️⃣ Defensive Programming Style

Extra safety checks

function max(a, b) {
  if (typeof a !== "number" || typeof b !== "number") {
    throw new Error("Invalid input");
  }
  return a > b ? a : b;
}

Characteristics:

  • Input validation
  • Error handling
  • Protects against misuse
  • More verbose but safer
Essential for libraries and public APIs where you can't control how your functions will be used.

5️⃣ Procedural Style

Step-by-step logic

function max(a, b) {
  let result;

  if (a > b) {
    result = a;
  } else {
    result = b;
  }

  return result;
}

Characteristics:

  • Explicit variable declaration
  • Step-by-step approach
  • More verbose than necessary
  • Clear control flow
This style can be useful for teaching programming concepts but is often unnecessarily verbose in production code.

6️⃣ Modular Style

Code split into reusable parts

// math.js
export function max(a, b) {
  return a > b ? a : b;
}

Characteristics:

  • Organized in modules
  • Uses ES6 import/export
  • Promotes code reuse
  • Better for larger projects
Modular programming is essential for maintaining large codebases and enables better code organization.

7️⃣ Functional Style

Pure function, no side effects

const max = (a, b) => Math.max(a, b);

Characteristics:

  • Leverages built-in functions
  • Declarative approach
  • Composable
  • No side effects
Functional programming emphasizes immutability and pure functions, making code more predictable and easier to test.

8️⃣ Object-Oriented Style (OOP)

Using a class

class MathUtil {
  max(a, b) {
    return a > b ? a : b;
  }
}

Characteristics:

  • Encapsulates functionality in classes
  • Groups related functions
  • Can have state and methods
  • Supports inheritance
OOP is useful for modeling real-world entities and organizing complex systems with many interacting parts.

9️⃣ Low-Level / Performance-Oriented Style

Explicit, minimal overhead

function max(a, b) {
  return a > b;
}

Characteristics:

  • Focuses on performance
  • May sacrifice correctness for speed
  • Low-level operations
  • Often optimized for specific cases
⚠️ Returns true or false, not the number (shows how low-level logic may leak abstraction)

🔟 Obfuscated Style 😈

Hard to read (don't do this in real life)

const _=($,$$)=>$>$$?$:$$;

Characteristics:

  • Intentionally confusing
  • Uses single-character variable names
  • Removes all whitespace
  • Makes code nearly impossible to understand
This style is sometimes used for code golfing or obfuscation, but should never be used in production code!

Final Advice

👉 Learn all styles

Understanding different approaches makes you a more versatile developer and helps you read code written by others.

👉 Use Clean + Modular by default

For most production code, prioritize readability and maintainability over cleverness or brevity.

👉 Use Ninja style only when teaching tricks or having fun

While elegant, concise code can be impressive, it's not always the best choice for team projects.

The best style often depends on the context: project requirements, team preferences, and the problem being solved.

Comments

As we know from the chapter Code structure, comments can be single-line: starting with // and multiline: /* ... */.

We normally use them to describe how and why the code works.

At first sight, commenting might be obvious, but novices in programming often use them wrongly.

Types of comments:

  • Single-line: // This is a comment
  • Multi-line: /* This is a multi-line comment */
  • Documentation: Special formats like JSDoc
Good comments can make code much easier to understand, but bad comments can be worse than no comments at all.

Bad Comments

Novices tend to use comments to explain "what is going on in the code". Like this: 

// This code will do this thing (...) and that thing (...)
// ...and who knows what else...
very;
complex;
code;
In good code, the amount of such "explanatory" comments should be minimal. Seriously, the code should be easy to understand without them.

Great rule:

"If the code is so unclear that it requires a comment, then maybe it should be rewritten instead."

Recipe: Factor Out Functions

Sometimes it's beneficial to replace a code piece with a function, like here:

Before:

function showPrimes(n) {
  nextPrime:
  for (let i = 2; i < n; i++) {

    // check if i is a prime number
    for (let j = 2; j < i; j++) {
      if (i % j == 0) continue nextPrime;
    }

    alert(i);
  }
}

After:

function showPrimes(n) {
  for (let i = 2; i < n; i++) {
    if (!isPrime(i)) continue;
    alert(i);
  }
}

function isPrime(n) {
  for (let i = 2; i < n; i++) {
    if (n % i == 0) return false;
  }
  return true;
}
Now we can understand the code easily. The function itself becomes the comment. Such code is called self-descriptive.

Recipe: Create Functions

And if we have a long "code sheet" like this:

Before:

// here we add whiskey
for(let i = 0; i < 10; i++) {
  let drop = getWhiskey();
  smell(drop);
  add(drop, glass);
}

// here we add juice
for(let t = 0; t < 3; t++) {
  let tomato = getTomato();
  examine(tomato);
  let juice = press(tomato);
  add(juice, glass);
}

After:

addWhiskey(glass);
addJuice(glass);

function addWhiskey(container) {
  for(let i = 0; i < 10; i++) {
    let drop = getWhiskey();
    //...
  }
}

function addJuice(container) {
  for(let t = 0; t < 3; t++) {
    let tomato = getTomato();
    //...
  }
}
Once again, functions themselves tell what's going on. There's nothing to comment. And also the code structure is better when split.

Good Comments - Architecture

So, explanatory comments are usually bad. Which comments are good?

Describe the architecture

Provide a high-level overview of components, how they interact, what's the control flow in various situations… In short – the bird's eye view of the code.

Example:

/**
 * This module handles user authentication.
 * 
 * Flow:
 * 1. User submits login form
 * 2. Credentials are validated against the database
 * 3. If valid, a JWT token is generated and stored
 * 4. User is redirected to dashboard
 * 
 * Components:
 * - LoginForm: Handles UI and form submission
 * - AuthService: Manages authentication logic
 * - TokenManager: Handles JWT token operations
 */
There's a special language UML to build high-level architecture diagrams explaining the code. Definitely worth studying.

Good Comments - Function Documentation

Document function parameters and usage. There's a special syntax JSDoc to document a function: usage, parameters, returned value.

Example:

/**
 * Returns x raised to the n-th power.
 *
 * @param {number} x The number to raise.
 * @param {number} n The power, must be a natural number.
 * @return {number} x raised to the n-th power.
 */
function pow(x, n) {
  ...
}

Benefits:

  • Helps understand the purpose of the function
  • Shows how to use it correctly
  • Many editors can provide autocomplete
  • Tools can generate HTML documentation
Many editors like WebStorm can understand JSDoc comments and use them to provide autocomplete and some automatic code-checking.

Good Comments - Why Solved This Way?

What's written is important. But what's not written may be even more important to understand what's going on. Why is the task solved exactly this way? The code gives no answer.

Example:

// Using a simple for-loop instead of Array.map()
// because it's 3x faster for large arrays
// and this is a performance-critical section
for (let i = 0; i < items.length; i++) {
  processItem(items[i]);
}

Why this matters:

  • Prevents "optimizations" that break the code
  • Documents design decisions
  • Explains non-obvious approaches
  • Saves time for future maintainers
Without such comments, you might think "How stupid I was then" and rewrite working code, only to discover why it was done that way.

Good Comments - Subtle Features

If the code has anything subtle and counter-intuitive, it's definitely worth commenting.

Example:

// Using parseInt instead of Math.floor for negative numbers
// because parseInt(-1.5) returns -1 while Math.floor(-1.5) returns -2
// and we need the behavior of truncating toward zero
let intValue = parseInt(floatValue);

Other examples of subtle features worth commenting:

  • Browser-specific workarounds
  • Non-obvious algorithm optimizations
  • Reasons for seemingly redundant code
  • Dependencies between distant parts of code
These comments are especially valuable because they explain the "why" behind code that might otherwise appear incorrect or inefficient.

Summary on Comments

An important sign of a good developer is comments: their presence and even their absence.

Good comments allow us to maintain the code well, come back to it after a delay and use it more effectively.

Comment this:

  • Overall architecture, high-level view
  • Function usage
  • Important solutions, especially when not immediately obvious

Avoid comments:

  • That tell "how code works" and "what it does"
  • Put them in only if it's impossible to make the code so simple and self-descriptive that it doesn't require them
Comments are also used for auto-documenting tools like JSDoc3: they read them and generate HTML-docs (or docs in another format).
