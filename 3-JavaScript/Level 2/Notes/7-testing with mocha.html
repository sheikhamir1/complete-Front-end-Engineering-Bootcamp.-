Why Do We Need Tests?

Imagine you write a function:

function pow(x, n) {
  return x ** n;
}

You might test it manually in the console:

pow(2,3) // 8
pow(3,4) // 81
But what if you change something in your function later? You might forget to check every previous case. Manual testing is error-prone and slow.
Solution: Automated testing runs all the checks for you, every time you change your code.

Behavior Driven Development (BDD)

BDD combines tests + documentation + examples.

Key BDD Components:

  • describe → group of tests, e.g., a function we are testing
  • it → a single test case or scenario
  • assert → checks if the actual output matches the expected output

Benefits of BDD:

  • Tests serve as documentation
  • Examples show how code should be used
  • Catches regressions automatically
  • Encourages better code design

Setting Up the Testing Environment in the Browser

We'll test a pow(x,n) function in a browser using Mocha + Chai.

Step 1: Create an HTML page

<!DOCTYPE html>
<html>
<head>
  <title>Mocha Test Demo</title>
  <!-- Mocha CSS -->
  <link rel="stylesheet" href="https://cdnjs.cloudflare.com/ajax/libs/mocha/3.2.0/mocha.css">
  <!-- Mocha JS -->
  <script src="https://cdnjs.cloudflare.com/ajax/libs/mocha/3.2.0/mocha.js"></script>
  <script>mocha.setup('bdd');</script>
  <!-- Chai JS -->
  <script src="https://cdnjs.cloudflare.com/ajax/libs/chai/3.5.0/chai.js"></script>
  <script>let assert = chai.assert;</script>
</head>
This HTML file includes Mocha for test running, Chai for assertions, and sets up BDD mode.

Setting Up (continued)

Step 2: Add body content

<body>
  <h1>Mocha Test Demo</h1>
  <div id="mocha"></div>

  <!-- Function to test -->
  <script>
    function pow(x, n) {
      // empty implementation for now
    }
  </script>

  <!-- Test spec -->
  <script src="test.js"></script>

  <!-- Run tests -->
  <script>mocha.run();</script>
</body>
</html>
The div with id="mocha" is where test results will be displayed. The function to test and the test spec are included as separate script files.

Writing the First Test (Spec)

Create a test.js file:

describe("pow", function() {

  it("raises 2 to the power 3", function() {
    assert.equal(pow(2, 3), 8);
  });

});

Explanation:

  • describe("pow", ...) → groups all tests for the pow function
  • it("raises 2 to the power 3", ...) → one test case
  • assert.equal(actual, expected) → checks if the function returns the expected value
If the function is empty, this test will fail, which is expected in BDD.

Running Tests in Browser

Steps to run tests:

  1. Open index.html in Chrome
  2. Mocha automatically shows test results in the <div id="mocha">
  3. You'll see the test fail (red), because pow is empty

Test results:

  • Red → Test failed
  • Green → Test passed
  • Mocha shows which test failed and why
This "red-green" cycle is a core part of BDD: write a failing test, then implement code to make it pass.

Implementing the Function

Write a dummy implementation first:

function pow(x, n) {
  return 8; // cheat, only works for 2^3
}

What happens now:

  • The first test now passes (green)
  • But pow(3, 4) would fail
  • This is expected - we're implementing incrementally
This approach of writing a minimal implementation to pass the test is called "Red-Green-Refactor" in TDD/BDD methodology.

Add More Tests

describe("pow", function() {

  it("2^3 = 8", function() {
    assert.equal(pow(2,3), 8);
  });

  it("3^4 = 81", function() {
    assert.equal(pow(3,4), 81);
  });

});

Key points:

  • Each it tests one specific thing
  • Tests should be independent of each other
  • When a test fails, Mocha shows exactly which test failed, making debugging easy
Our current implementation will pass the first test but fail the second one. This drives us to improve the implementation.

Writing a Real Implementation

function pow(x, n) {
  let result = 1;
  for (let i = 0; i < n; i++) {
    result *= x;
  }
  return result;
}

What this does:

  • Starts with result = 1
  • Multiplies result by x, n times
  • Returns the final result
All tests now pass. ✅ This is a correct implementation for positive integer powers.

Using Loops to Generate Tests

You can generate tests dynamically for multiple inputs:

describe("pow", function() {
  for (let x = 1; x <= 5; x++) {
    it(`${x}^3 = ${x*x*x}`, function() {
      assert.equal(pow(x, 3), x*x*x);
    });
  }
});

Benefits of this approach:

  • Checks many cases automatically
  • No need to write each test manually
  • Template literals make test descriptions clear
This is especially useful for testing functions with many valid input combinations.

Nested describe for Organization

describe("pow", function() {

  describe("raises x to the power 3", function() {
    for (let x = 1; x <= 5; x++) {
      it(`${x}^3 = ${x*x*x}`, function() {
        assert.equal(pow(x, 3), x*x*x);
      });
    }
  });

});

Benefits of nesting:

  • Helps group similar tests
  • Output in Mocha is indented, making it easy to read
  • Can apply hooks to specific groups
You can nest describe blocks as deeply as needed to organize your tests logically.

before/after and beforeEach/afterEach

describe("demo hooks", function() {
  before(() => console.log("All tests starting"));
  after(() => console.log("All tests finished"));

  beforeEach(() => console.log("Before a test"));
  afterEach(() => console.log("After a test"));

  it("test 1", () => console.log("Running test 1"));
  it("test 2", () => console.log("Running test 2"));
});

Hook types:

  • before → runs once before all tests
  • after → runs once after all tests
  • beforeEach → runs before every it
  • afterEach → runs after every it
Hooks are useful to reset state between tests or set up/tear down resources.

Adding Edge Case Tests

describe("pow", function() {
  it("negative n returns NaN", function() {
    assert.isNaN(pow(2,-1));
  });

  it("non-integer n returns NaN", function() {
    assert.isNaN(pow(2,1.5));
  });
});

Our function must now handle invalid inputs:

function pow(x, n) {
  if (n < 0 || Math.round(n) !== n) return NaN;
  let result = 1;
  for (let i = 0; i < n; i++) result *= x;
  return result;
}
Tests fail first (red), then pass after implementation (green). This is BDD in action: tests first, then implementation.

Summary

BDD Workflow:

  1. Write a test spec first
  2. Implement the function to pass the test
  3. Add more tests for other cases

Benefits of Mocha + Chai:

  • Automates all tests, no manual checking
  • Tests act as documentation, examples, and safety checks
  • Use hooks (before, after, etc.) for setup/cleanup
BDD ensures robust, well-structured, maintainable code by making you think about expected behavior before implementation.
