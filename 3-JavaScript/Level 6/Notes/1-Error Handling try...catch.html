Error Handling: try...catch

Saving your scripts from crashing

No matter how carefully we code, errors happen—bad user input, network failures, or unexpected server responses. Normally, a script "dies" immediately when an error occurs.

Real-World Analogy: The Airbag 🚗
Driving a car is like running code inside a try block. If you crash (an error occurs), you don't want the journey to end fatally (script dies). The catch block is the airbag—it deploys to handle the crash safely so you can keep going or exit gracefully.

The "try...catch" Syntax

How to catch an error before it kills your app

Basic Structure

try {
  // Code that might fail
} catch (err) {
  // Code that runs ONLY if an error occurs
}

How it works:

  • No errors: The try block runs top to bottom, and the catch block is completely ignored.
  • Error occurs: Execution stops immediately inside try, and the script jumps to the catch block. The script survives!
Crucial Rule: try...catch only works for runtime errors (exceptions). It will NOT catch syntax errors (like missing curly braces) because the engine can't even read/parse the code to begin with.

The Error Object & Synchronous Gotchas

Understanding the details of a caught error

When an error is caught, JavaScript passes an error object to the catch block. This object contains vital debugging information.

Property What it means Example
err.name The type of error. ReferenceError
err.message The human-readable text about the error. "lalala is not defined"
err.stack The call stack (where it happened). Great for debugging. "ReferenceError: lalala... at line 5"

The Synchronous Catch

try...catch won't catch errors inside scheduled code like setTimeout because by the time the scheduled function runs, the engine has already left the try block. Fix: Put the try...catch inside the setTimeout function!

Real-World Use Case: JSON Parsing

Handling bad data from a server

When we fetch data from a server, we use JSON.parse() to turn text into a JavaScript object. If the data is malformed, JSON.parse() crashes the script.

Bad (No Catch)

let json = "{ bad json }";
let user = JSON.parse(json);
// Script dies here. 
// User sees nothing.

Good (With try...catch)

let json = "{ bad json }";
try {
  let user = JSON.parse(json);
} catch (err) {
  alert("Sorry, bad data!");
  // Script keeps running!
}
Optional Catch Binding: If you don't need to look at the error object details, modern JavaScript allows you to omit it entirely: catch { ... } instead of catch (err) { ... }.

Throwing Our Own Errors

Creating custom errors with "throw"

Sometimes the data is technically valid JSON, but logically wrong for our app (e.g., a user object without a name). We can manually throw an error using the throw operator.

Using Built-in Error Constructors

let json = '{ "age": 30 }'; // Valid JSON, but missing name!

try {
  let user = JSON.parse(json);

  if (!user.name) {
    throw new SyntaxError("Incomplete data: no name");
  }

} catch (err) {
  alert( "JSON Error: " + err.message ); 
  // Catches both JSON.parse errors 
  // AND our custom thrown error!
}
Why use built-in constructors? You can throw anything (even a string), but it's best practice to use objects like new Error(), new SyntaxError(), or new TypeError() because they automatically generate the correct name and message properties, and capture the stack trace.

Rethrowing Errors

Only catch what you can handle

A catch block catches all errors. But what if a different, unexpected error happens (like a typo in your code)? You shouldn't mask it with a generic "JSON Error" message. You should let it pass through.

The Rethrowing Pattern

try {
  // ...
  blabla(); // Unexpected error (typo)
} catch (err) {
  if (err instanceof SyntaxError) {
    // We know how to handle this specific error
    alert( "JSON Error: " + err.message );
  } else {
    // We don't know what this is. Throw it back!
    throw err; 
  }
}
Analogy: The Mail Sorter 📬
The catch block is like a mail sorter. You only take the letters addressed to you (SyntaxError). Everything else you put back in the outgoing mail (rethrow) so the main post office (global error handler) can deal with it.

The "finally" Clause

Code that runs no matter what

The finally block executes after try (if no errors) or after catch (if there was an error). It runs always, even if you use return or throw inside the try/catch.

Use Case: Measuring Execution Time

Start a timer before the try, and stop the timer inside finally. This guarantees you'll get the measurement regardless of whether the function succeeded or crashed.

try...finally (No catch)

You can even omit catch entirely! This is useful when you want to ensure cleanup happens (like closing a connection or stopping a loading spinner), but you want the error to still propagate up to the caller. 

function func() {
  try {
    // do work that might fail
  } finally {
    // cleanup, no matter what
  }
}

Global Catch

Catching errors that slip through the cracks

What if a fatal error happens outside of any try...catch? Normally, the script dies silently. Modern environments provide a "global catch" to log these crashes.

In the Browser

We can assign a function to window.onerror. It catches the error message, URL, and line number. 

window.onerror = function(
  message, url, line, col, error
) {
  // Log error to a service
};

In Node.js

We use the uncaughtException event on the process object.

process.on(
  "uncaughtException", 
  function(err) {
  // Log error
});
Real-World Application: Global handlers aren't meant to recover the script (the app is likely in a bad state). They are used to send crash reports to services like Sentry or Muscula so developers can fix bugs they didn't know existed!
