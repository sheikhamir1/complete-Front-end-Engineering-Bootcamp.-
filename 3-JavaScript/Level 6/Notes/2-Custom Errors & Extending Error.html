Custom Errors & Extending Error

Building a hierarchy of specific, helpful errors

Built-in errors like Error or SyntaxError are great, but as apps grow, we need specific errors for specific problems: HttpError, DbError, NotFoundError, etc.

Real-World Analogy: Medical Diagnosis 🏥
A generic Error is like a doctor saying "You are sick." It's true, but not helpful. Custom Errors are like a doctor saying "You have a specific bacterial infection." It tells you exactly what went wrong and how to treat it. Plus, custom errors can carry extra data (like an HTTP status code 404).

Extending the Error Class

Creating our own specific error types

Technically, you can throw anything (even a string). But if we create a class that inherits from Error, we can use instanceof Error to identify it easily.

Inside the built-in Error class

class Error {
  constructor(message) {
    this.message = message;
    this.name = "Error"; 
    this.stack = <call stack>; // Non-standard but widely supported
  }
}

Our Custom: ValidationError

class ValidationError extends Error {
  constructor(message) {
    super(message); // 1. Call parent constructor (required!)
    this.name = "ValidationError"; // 2. Override the name
  }
}
Why set this.name? The parent Error constructor automatically sets this.name = "Error". If we don't manually reset it to "ValidationError" after calling super(), our error will incorrectly report itself as a generic Error.

Using Custom Errors

Throwing and catching specific issues

Let's say we are reading user data. The JSON might be valid, but missing required fields (like name or age). This is a perfect use case for ValidationError.

Implementation

function readUser(json) {
  let user = JSON.parse(json);

  if (!user.age) {
    throw new ValidationError("No field: age");
  }
  if (!user.name) {
    throw new ValidationError("No field: name");
  }
  return user;
}

try {
  let user = readUser('{ "age": 25 }');
} catch (err) {
  if (err instanceof ValidationError) {
    alert("Invalid data: " + err.message);
  } else if (err instanceof SyntaxError) {
    alert("JSON Syntax Error: " + err.message);
  } else {
    throw err; // Rethrow unknown errors!
  }
}
Pro Tip: Always use err instanceof ValidationError rather than checking err.name == "ValidationError". instanceof respects inheritance, so it will still work if you create sub-classes of ValidationError later!

Deepening the Hierarchy

Getting more specific with PropertyRequiredError

ValidationError is good, but we can get more specific. Let's make PropertyRequiredError that automatically knows which property is missing.

Adding Custom Properties

class PropertyRequiredError extends ValidationError {
  constructor(property) {
    super("No property: " + property); // Set the message
    this.name = "PropertyRequiredError";
    this.property = property; // Attach extra data!
  }
}

// Usage:
throw new PropertyRequiredError("age");

The Base Class Trick

Setting this.name manually in every class is tedious. Create a base class that does it automatically: this.name = this.constructor.name;. Then, all your custom errors inherit from that base class instead of Error directly!

Wrapping Exceptions

Simplifying error handling for the caller

As functions grow, they can throw many types of errors (SyntaxError, ValidationError, DatabaseError, etc.). Forcing the caller to check for every single type is exhausting.

Solution: Wrap low-level errors into one generic, high-level error (like ReadError).

The ReadError Wrapper

class ReadError extends Error {
  constructor(message, cause) {
    super(message);
    this.cause = cause; // The original low-level error!
    this.name = 'ReadError';
  }
}

function readUser(json) {
  try {
    let user = JSON.parse(json);
    // validation logic...
  } catch (err) {
    // Wrap any known error into a ReadError
    if (err instanceof SyntaxError || err instanceof ValidationError) {
      throw new ReadError("Reading failed", err);
    } else {
      throw err; // Rethrow unknown errors
    }
  }
}
Analogy: The Company Receptionist 🕵️‍♂️
You don't need to know the specific internal departments (Syntax, Validation, etc.). You just talk to the Receptionist (ReadError). If you need the deep details, the receptionist can give you the original memo (e.cause), but 90% of the time, just knowing "Reading failed" is enough.

Wrapping Exceptions in Action

How the caller handles wrapped exceptions

Now, the code that calls readUser() only needs to check for one single error type: ReadError. It doesn't need to care about the underlying specifics.

Clean Calling Code

try {
  readUser('{bad json}');
} catch (e) {
  if (e instanceof ReadError) {
    alert(e.message); // "Reading failed"
    
    // We can still access the original error if we need it!
    alert("Original error: " + e.cause); 
    // "SyntaxError: Unexpected token..."
  } else {
    throw e; // Rethrow unexpected errors
  }
}
Why is this powerful?
1. Decoupling: The calling code doesn't need to know the internal implementation details of readUser.
2. Flexibility: You can add new low-level errors inside readUser later, and the calling code won't break—as long as you wrap them in ReadError.
