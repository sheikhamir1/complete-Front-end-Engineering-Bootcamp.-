Error Handling with Promises

Catching failures in asynchronous code

Promise chains are great at error handling. When a promise rejects, the control immediately jumps to the closest rejection handler (`.catch`), skipping the rest of the chain.

Real-World Analogy: The Factory Safety Net 🏭
Imagine an assembly line with 3 stations, and a big safety net at the end. If a product breaks at station 1, 2, or 3, it falls off the belt and is caught by the safety net (.catch). You don't need a net at every single station—just one at the bottom catches everything.

Catching Errors in Chains

One catch to rule them all

The easiest way to handle errors in a sequence of async tasks is to append a single .catch at the very end of the chain.

Example: Network Request Chain

fetch('https://no-such-server.blabla') // Rejects!
  .then(response => response.json())
  .then(user => fetch(`https://api.github.com/users/${user.name}`))
  .then(response => response.json())
  .catch(err => alert(err)); // Catches ANY error above!

If the first fetch fails, the entire chain is skipped, and the error drops straight into .catch. But if the first fetch succeeds and the second fails, .catch still gets it!

Convenience: You don't need to check for errors after every single step. A single .catch at the bottom acts as a safety net for the entire chain.

Implicit try...catch

Throwing vs. Rejecting

The code inside a promise executor and .then handlers has an "invisible try..catch" around it. If you throw an error, it is automatically caught and treated as a rejection!

Explicit Reject

new Promise((resolve, reject) => {
  reject(new Error("Whoops!"));
}).catch(alert); // Error: Whoops!

Implicit Throw

new Promise((resolve, reject) => {
  throw new Error("Whoops!");
}).catch(alert); // Error: Whoops!

Works inside .then() too!

new Promise((resolve, reject) => {
  resolve("ok");
}).then((result) => {
  blabla(); // No such function! (ReferenceError)
}).catch(alert); // Catches the accidental error!
Key Takeaway: .catch catches not just explicit reject() calls, but also accidental programming errors (like typos) in the handlers above.

Rethrowing Errors

Handling what you can, passing what you can't

Just like regular try...catch, we can analyze an error in .catch. If we can handle it, the chain continues to the next successful .then. If we can't handle it, we can rethrow it to the next error handler.

Example: Handled successfully

new Promise((resolve, reject) => {
  throw new Error("Whoops!");
}).catch(function(error) {
  alert("The error is handled, continue normally");
  // No throw = error is swallowed, chain continues
}).then(() => alert("Next successful handler runs"));

Example: Rethrowing

new Promise((resolve, reject) => {
  throw new Error("Whoops!");
}).catch(function(error) {
  if (error instanceof URIError) {
    // Handle it
  } else {
    alert("Can't handle such error");
    throw error; // Rethrows to the next catch!
  }
}).catch(error => alert(`The unknown error: ${error}`));
Analogy: The Triage Nurse 🏥
A patient (error) arrives. The nurse (.catch) checks it. If it's a minor cut, they treat it and send the patient home (continue to .then). If it's major surgery, they send the patient to the specialist (rethrow to next .catch).

Unhandled Rejections

What happens when errors get stuck?

What if an error occurs but there's no .catch to handle it? The error gets "stuck". In real life, this means something went terribly wrong silently.

The Global Catch: unhandledrejection

Modern JavaScript tracks unhandled rejections. In the browser, we can catch these "stuck" errors using a global event called unhandledrejection. 

window.addEventListener('unhandledrejection', function(event) {
  // event.promise: the promise that generated the error
  // event.reason: the unhandled error object
  alert(event.reason); 
});

new Promise(function() {
  throw new Error("Whoops!");
}); // No catch attached!
Analogy: The Fire Alarm 🚨
If a fire (error) breaks out and no one is there to put it out (no .catch), the building's global fire alarm (unhandledrejection) goes off. It doesn't fix the fire, but it alerts everyone (including developers) that something catastrophic happened.

Summary

Best practices for promise error handling

1. .catch catches everything

It catches explicit reject() calls AND accidental throw errors in handlers above it.

2. Analyze and Rethrow

Place .catch where you know how to handle specific errors. If you encounter an error you can't handle, rethrow it for the next handler.

3. The Global Safety Net

Always set up the unhandledrejection event handler on window. This ensures your app never "just dies" silently if a .catch is forgotten.
