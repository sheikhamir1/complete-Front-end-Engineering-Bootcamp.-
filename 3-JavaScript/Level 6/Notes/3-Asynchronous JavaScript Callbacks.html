Asynchronous JavaScript: Callbacks

Handling actions that take time

In JavaScript, some actions take time—like downloading a file or fetching data. These are called asynchronous actions: we start them now, but they finish later.

Real-World Analogy: The Coffee Shop ☕
When you order a coffee, you don't stand frozen at the counter blocking everyone else while it brews (synchronous). Instead, you step aside and give the barista your name. When the coffee is ready, they call your name so you can pick it up. In JavaScript, that "name" is a Callback.

The Problem: Code Doesn't Wait

Why synchronous thinking fails in async situations

Let's look at a function that loads a script onto our webpage. It creates a <script> tag and appends it. The browser starts loading it in the background.

The Naive Approach (Fails!)

function loadScript(src) {
  let script = document.createElement('script');
  script.src = src;
  document.head.append(script);
}

loadScript('/my/script.js'); // Starts loading
newFunction(); // ERROR! The script hasn't loaded yet!

Why does it fail?

Because loadScript is asynchronous. JavaScript doesn't wait for the file to download before moving to the next line of code. By the time we call newFunction(), the script isn't ready yet.

Key Takeaway: Code below an asynchronous action executes immediately. It does NOT wait for the async action to finish.

The Solution: Callbacks

Passing a function to be executed *later*

To know when an async action finishes, we can pass a function as an argument—the callback—and tell the async function to run it when it's done.

The Callback Approach (Works!)

function loadScript(src, callback) {
  let script = document.createElement('script');
  script.src = src;

  // When the script finishes loading, call the callback!
  script.onload = () => callback(script);

  document.head.append(script);
}

// Pass what we want to happen AFTER it loads
loadScript('/my/script.js', function() {
  newFunction(); // Now it works perfectly!
});
Analogy: "Here is the script to load. When it's loaded, call me back so I can use the new functions." The second argument is the callback function.

Callback in Callback

Handling sequences of asynchronous actions

What if we need to load two scripts one after another? The natural solution is to put the second loadScript call inside the first callback. 

loadScript('/my/script1.js', function(script) {
  alert('Script 1 loaded!');

  // Load the second script inside the first callback
  loadScript('/my/script2.js', function(script) {
    alert('Script 2 loaded!');
  });
});

It works... but there's a catch

For one or two actions, this is fine. But what if we need to load 3, 4, or 5 scripts sequentially? Every new action requires a deeper level of nesting.

Handling Errors

The "Error-First" callback style

What if the script fails to load (e.g., network error)? Our callback needs a way to report success OR failure. The standard convention in JavaScript is the Error-First Callback.

The Convention

  • First argument: Reserved for an error (if one occurred). callback(err)
  • Second argument: Reserved for the successful result. callback(null, result) 
function loadScript(src, callback) {
  let script = document.createElement('script');
  script.src = src;

  script.onload = () => callback(null, script); // Success: null error
  script.onerror = () => callback(new Error(`Failed: ${src}`)); // Fail: error object

  document.head.append(script);
}
Rule of Thumb: If the first argument error is not null, something went wrong. If it is null, the operation succeeded, and you can safely use the second argument.

The Pyramid of Doom

When callbacks get out of control

Combining sequential loading with error-first callbacks creates deeply nested code. This is famously known as "Callback Hell" or the "Pyramid of Doom". 

loadScript('1.js', function(error, script) {
  if (error) { handleError(error); } 
  else {
    loadScript('2.js', function(error, script) {
      if (error) { handleError(error); } 
      else {
        loadScript('3.js', function(error, script) {
          if (error) { handleError(error); } 
          else {
            // We are 4 levels deep!
          }
        });
      }
    });
  }
});
Analogy: Inception 🧠
It's like a dream within a dream within a dream. Every time you add an async step, you go one level deeper. The code drifts rapidly to the right, making it incredibly hard to read, manage, and debug.

A Flawed Fix & The Real Solution

Moving toward Promises

The Flawed Fix: Named Functions

We can flatten the pyramid by taking the anonymous callbacks and turning them into named functions. 

loadScript('1.js', step1);

function step1(error, script) {
  if (error) { handleError(error); } 
  else { loadScript('2.js', step2); }
}

function step2(error, script) {
  if (error) { handleError(error); } 
  else { loadScript('3.js', step3); }
}

Why isn't this ideal?

While it fixes the deep nesting, the code looks like a torn-apart spreadsheet. You have to constantly eye-jump between functions to understand the flow. Plus, these step functions are only used once, cluttering the namespace.

The Real Solution: Promises

Luckily, modern JavaScript offers a much better way to handle sequential asynchronous operations without nesting or eye-jumping: Promises. They allow code to be written in a flat, top-to-bottom chain.
