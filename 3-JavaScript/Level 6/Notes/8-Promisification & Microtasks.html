Promisification & Microtasks

Upgrading callbacks and understanding the Promise queue

Many older libraries use callbacks, but promises are much easier to work with. We need a way to convert them. Also, to truly master promises, we must understand how they schedule their code behind the scenes using "Microtasks".

Real-World Analogies 🏭🎟️
Promisification: Upgrading an old appliance with a modern plug adapter so it fits your new outlets.
Microtasks: A VIP fast-pass line at a theme park. Regular code runs on the main line, but Promise handlers get to cut to the front as soon as the main line takes a break.

What is Promisification?

Converting callbacks to promises

Promisification is the conversion of a function that accepts a callback into a function that returns a Promise. It makes old code compatible with modern async/await and promise chains.

Before: Callback-based

function loadScript(src, callback) {
  let script = document.createElement('script');
  script.src = src;
  script.onload = () => callback(null, script);
  script.onerror = () => callback(new Error(`Load error`));
  document.head.append(script);
}

After: Promisified Wrapper

let loadScriptPromise = function(src) {
  return new Promise((resolve, reject) => {
    loadScript(src, (err, script) => {
      if (err) reject(err);
      else resolve(script);
    });
  });
};

// Much cleaner usage!
loadScriptPromise('my.js').then(script => ...);

The Promisify Helper

Automating the conversion process

Writing a custom wrapper for every single function is tedious. Instead, we can create a helper function promisify(f) that automatically converts any error-first callback function into a promise!

Universal Promisify Function

function promisify(f) {
  return function (...args) { // Return a wrapper
    return new Promise((resolve, reject) => {
      function callback(err, result) { // Custom callback
        if (err) reject(err);
        else resolve(result);
      }
      args.push(callback); // Add callback to arguments
      f.call(this, ...args); // Call the original function
    });
  };
}

// Usage:
let loadScriptPromise = promisify(loadScript);
loadScriptPromise('my.js').then(script => alert('Loaded!'));
Analogy: The Universal Translator 🤖
Instead of learning a new language (writing a wrapper) for every old function, you build a Universal Translator (promisify). You just feed it the old function, and it outputs a modern version that speaks "Promises".

Advanced Promisification

Handling multiple callback results

What if the original callback returns multiple arguments, like callback(err, res1, res2)? A Promise can only resolve with one value. To fix this, we use an advanced promisify that returns an array of results.

Promisify with manyArgs

function promisify(f, manyArgs = false) {
  return function (...args) {
    return new Promise((resolve, reject) => {
      function callback(err, ...results) {
        if (err) reject(err);
        else resolve(manyArgs ? results : results[0]);
      }
      args.push(callback);
      f.call(this, ...args);
    });
  };
}

// Usage:
const fPromise = promisify(f, true);
fPromise(...).then(arrayOfResults => ...);

Important Limitation!

Promisification is only for functions that call the callback once. If a function calls its callback multiple times (like an onmousemove handler), the Promise will only resolve on the first call. Later calls are ignored!

Microtasks: The Async Secret

Why promise handlers are always delayed

Promise handlers (.then, .catch, .finally) are always asynchronous. Even if a promise resolves instantly, the code below .then will still execute first.

The Weird Behavior

let promise = Promise.resolve();

promise.then(() => alert("promise done!"));

alert("code finished"); // THIS ALERT SHOWS FIRST!

Why does this happen?

Because of the Microtask Queue (internal name: PromiseJobs). When a promise is ready, its .then handler is put into this queue. The JavaScript engine finishes the current code first, and then looks in the queue.

The Rule: Execution of a microtask is initiated only when nothing else is running. The main code always takes priority over the microtask queue.

Forcing Order with Microtasks

Guaranteeing execution sequence

What if we absolutely need "code finished" to run after "promise done"? Simple: put it inside a .then()! This adds it to the microtask queue in the correct order.

Wrong Order

Promise.resolve()
  .then(() => alert("promise done!"));

alert("code finished"); 
// Output: 
// 1. code finished
// 2. promise done!

Right Order

Promise.resolve()
  .then(() => alert("promise done!"))
  .then(() => alert("code finished"));

// Output: 
// 1. promise done!
// 2. code finished

Unhandled Rejections Explained

How the microtask queue tracks errors

Now we can understand exactly how the browser detects an "unhandled rejection". It happens when the microtask queue finishes, and a promise is still rejected with no .catch.

Too Late to Catch!

let promise = Promise.reject(new Error("Failed!"));

// We catch it, but inside a setTimeout (Macrotask)
setTimeout(() => promise.catch(err => alert('caught')), 1000);

// The unhandledrejection event STILL fires!
window.addEventListener('unhandledrejection', event => {
  alert(event.reason); // Error: Failed!
});
Why did it fire? The unhandledrejection event checks the promise state immediately after the microtask queue is empty. Because setTimeout is a "macrotask" and runs much later, the engine thinks the error was forgotten by the time the microtask queue finishes!
