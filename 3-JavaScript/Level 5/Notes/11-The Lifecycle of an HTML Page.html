The Lifecycle of an HTML Page

Understanding Page Loading, Scripts, and Resources

Just like a building has stages—foundation, structure, and finally moving furniture—an HTML page goes through a lifecycle from the moment a user requests it to the moment they leave.

Real-World Analogy: Building a House 🏠
1. DOMContentLoaded: The house structure is built. You can walk through rooms, but no furniture or paint is there yet.
2. Load: The house is fully finished. Furniture is moved in, pictures are hung.
3. Beforeunload/Unload: You are moving out and turning off the lights.

The 3 Main Lifecycle Events

What happens and when?

1. DOMContentLoaded

The browser fully loaded the HTML and built the DOM tree. However, external resources like images and stylesheets may not be loaded yet.
Use case: Safe to search for DOM nodes and initialize your interface.

2. Load

Not only is the HTML loaded, but ALL external resources (images, styles, iframes) are finished downloading.
Use case: You can now safely get image sizes or check applied CSS styles.

3. Beforeunload / Unload

The user is leaving the page.
Use case (beforeunload): Ask the user "Are you sure? You have unsaved changes!"
Use case (unload): Send final analytics data to the server.

Important: Always use document.addEventListener("DOMContentLoaded", ready); instead of document.onDOMContentLoaded.

DOMContentLoaded Deep Dive

What blocks the DOM from being ready?

Scripts Block It

When the browser finds a <script>, it must execute it before continuing to build the DOM. This is because scripts might modify the HTML.

Exceptions: Scripts with async or dynamically created scripts do NOT block DOMContentLoaded.

Styles & Scripts

External stylesheets don't block DOMContentLoaded. BUT, if a script comes after a stylesheet, the script must wait for the style to load. Since DOMContentLoaded waits for scripts, it indirectly waits for styles too.

Browser Autofill

Did you know browsers try to autofill your login details on DOMContentLoaded? If your page has scripts that delay this event, the autofill gets delayed too. That's why some sites take a second to auto-fill your password!

Analogy: You can't hang a picture (script) until the paint (stylesheet) dries. And you can't finish building the room (DOMContentLoaded) until the picture is hung!

Leaving the Page: Unload & Beforeunload

Handling user exits safely

Beforeunload - The "Are you sure?" Prompt

When a user tries to close the tab or navigate away, beforeunload triggers. If you cancel this event, the browser warns the user.

Crucial Note: Modern browsers ignore custom messages in this prompt (to prevent malicious sites from scamming users). You must use event.returnValue instead of event.preventDefault().

Unload - The "Goodbye" Data Send

When the user is finally leaving, you can't show alerts or delay them. However, you can send data (like analytics) to your server using navigator.sendBeacon(url, data).

Why use sendBeacon?

It sends data in the background. It doesn't block the user from leaving, it limits data to 64kb, and it ensures the data reaches the server even though the page is closing.

document.readyState

Checking the current loading status

What if your script runs after the page is already loaded? DOMContentLoaded won't fire! You can check document.readyState to see where you are in the lifecycle.

State Meaning Real-World Analogy
loading The document is still loading. 🚚 The delivery truck is on the way.
interactive The document is parsed. Happens right before DOMContentLoaded. 📦 The boxes are in the house, waiting to be unpacked.
complete The document and all resources are loaded. Same time as window.onload. 🏠 Everything is unpacked and put away.
Pro Tip: You can use the readystatechange event to track these changes, but it's rarely used today because DOMContentLoaded and load are much simpler.

Scripts: async vs defer

Solving the "blocking script" problem

Normally, when the browser hits a <script>, it stops building the page, downloads the script, and runs it. This blocks the user from seeing the page. async and defer fix this.

defer

Tells the browser: "Download this in the background, but DON'T block the page. Run it only AFTER the HTML is fully parsed."

  • Never blocks the page.
  • Runs before DOMContentLoaded.
  • Keeps document order. (If script 1 is before script 2, script 1 runs first, even if script 2 downloads faster).

Analogy: A take-a-number system at a deli. Scripts run in the order they were added to the page.

async

Tells the browser: "Download this in the background, and run it AS SOON AS it's ready, regardless of anything else."

  • Never blocks the page.
  • Does NOT wait for DOMContentLoaded.
  • Load-first order. (Whichever script downloads first, runs first. Order in HTML doesn't matter).

Analogy: Fast-pass tickets at an amusement park. Independent scripts (like Google Analytics or Ads) run as soon as they arrive.

Dynamic Scripts

Loading scripts on the fly with JavaScript

You can create and add a script using JavaScript itself. These scripts behave as async by default—meaning they run as soon as they load.

Default Dynamic Script (Async behavior)

let script = document.createElement('script');
script.src = "myScript.js";
document.body.append(script); // Runs as soon as it loads

Forcing Order in Dynamic Scripts (Defer behavior)

If you need dynamic scripts to run in a specific order, explicitly set async = false. 

let script1 = document.createElement('script');
script1.src = "library.js";
script1.async = false; // Forces document order

let script2 = document.createElement('script');
script2.src = "app.js";
script2.async = false; // Will wait for library.js to finish first

document.body.append(script1);
document.body.append(script2);
Best Practice: If your page uses defer/async, users might see the page before scripts initialize. Always show "loading" indicators and disable buttons until scripts are ready!

Resource Loading: onload & onerror

Tracking success and failure of external files

onload

Triggers when a resource (like an image or script) successfully loads and executes.

Use case: Running a function that relies on a 3rd-party library, only after that library is fully downloaded.

onerror

Triggers when the loading fails (e.g., 404 error, server down).

Limitation: You can't get specific HTTP error details (like 404 vs 500). You only know it failed.

Important Exceptions

  • Images: Start loading as soon as the src attribute is set, even before they are added to the page.
  • Iframes: Trigger onload even if the page inside isn't found (404). For historical reasons, it counts as "loaded" if the iframe frame itself rendered.
Note: onload/onerror only track the *loading* of the file. If a script loads successfully but contains a bug (syntax error), onload still triggers! Use window.onerror for script bugs.

Crossorigin Policy (CORS)

Why can't I see errors from other domains?

Security rules prevent scripts on your site from reading the details of scripts from another site. This means if an external script throws an error, you only see Script error. with no details.

Real-World Analogy: A package arrives from another country without a customs declaration. You know it arrived (loaded), but security won't let you open it to see what went wrong inside.

Attribute Effect Server Headers Required
No attribute Access prohibited. You get no error details. N/A
crossorigin="anonymous" Access allowed. No cookies sent to the remote server. Access-Control-Allow-Origin: *
crossorigin="use-credentials" Access allowed. Sends cookies/authorization. Access-Control-Allow-Origin: [your domain] AND Access-Control-Allow-Credentials: true
Takeaway: If you manage the external server, add the crossorigin attribute to your script tags and configure the server to send the right headers so you can actually debug errors!
